# 实验二 初始 SRS 分析（摘要）

- 项目代号：**CampusEvent**（校园活动报名与管理系统）
- 阶段：第 1 周 · 初始版本（baseline-v1 之前的需求基线）
- 依据：《实验二指导书》3.2 初始业务需求、3.5 验收用例、附录 B
- 文档性质：需求摘要，用于后续用例说明、UML 类图与编码的输入；不包含设计实现细节

## 1. 系统范围与角色

### 1.1 角色

| 角色 | 说明 | 主要字段 |
|---|---|---|
| Student（学生） | 浏览活动、报名/取消报名、查看自己的站内消息 | student_id（唯一）、name |
| Admin（管理员） | 创建/编辑/删除活动、审批待审核报名、查看统计 | 无持久化字段：管理员为内存模拟角色，不入库 |

- **不做登录注册**：使用固定演示账号，进入系统即选择身份（或通过页面顶部切换账号）。
  - 演示学生：S001 / 张三，S002 / 李四，S003 / 王五
  - 管理员：内置模拟角色，直接以“管理员”身份进入，不需要账号 ID，不写入数据库
- **不做复杂权限系统**：V1 不校验接口调用者身份，管理端接口仅靠前端入口区分。这是有意简化，需在报告中说明。

### 1.2 范围内功能

P2-F01 ~ P2-F08（见第 3 节）。

### 1.3 明确不做（Out of Scope）

1. **没有用户注册、登录、密码、会话、第三方认证**；只用固定演示账号。
2. **没有消息队列 / 消息中间件**；站内通知在进程内通过观察者或事件分发完成。
3. **没有后续变更需求**：第 2 周教师发布的变更单（CR）在初版验收前不获取、不设计、不实现。
4. 不做邮件/短信/微信等外部通知渠道；不做消息已读提醒、未读数、消息删除等增强功能（is_read 字段仅预留）。
5. 不做多租户、分页导出、文件上传、活动图片等需求外功能。
6. 不做并发集群部署；V1 为单体应用 + 单数据库。

## 2. 领域数据（附录 B.1）

| 对象 | 建议主要字段 | 约束 |
|---|---|---|
| Student | student_id、name | 学生 ID 唯一 |
| Activity | activity_id、title、category、start_at、location、capacity、policy_type | 容量为正整数；活动开始前允许报名 |
| Registration | registration_id、activity_id、student_id、status、created_at、updated_at | 状态仅限：待审核 / 已通过 / 已拒绝 / 已取消 |
| Message | message_id、student_id、activity_id、content、created_at、is_read | 报名或审核动作可产生站内消息 |

注：Admin 不属于持久化领域对象，仅作为内存中的角色标识参与界面路由与操作入口区分。

补充约定：

- `policy_type` 取值：`DIRECT`（直接报名）、`APPROVAL`（管理员审核）。
- `status` 取值：`PENDING`（待审核）、`APPROVED`（已通过）、`REJECTED`（已拒绝）、`CANCELLED`（已取消）。
- **数据必须持久化**：使用文件型数据库（V1 建议 SQLite，如 `campus_event.db`），服务重启后活动、报名、通知数据保持一致（验收用例 C10）。

## 3. 功能需求复述（P2-F01 ~ P2-F08）

| 编号 | 功能模块 | 复述（V1 要做什么） |
|---|---|---|
| P2-F01 | 活动管理 | 管理员创建、编辑、删除活动；可设置名称、类型（分类）、开始时间、地点、人数上限、报名方式（直接报名/审核）。创建时校验名称、时间、地点必填，容量为正整数。 |
| P2-F02 | 活动查看 | 学生查看活动列表与活动详情；支持按活动名称关键字筛选。列表与详情展示名称、分类、时间、地点、人数上限、报名方式、当前报名情况。 |
| P2-F03 | 报名/取消 | 学生可对活动报名、取消自己的报名；**禁止同一学生对同一活动产生重复的有效报名**（有效 = 待审核或已通过）。 |
| P2-F04 | 报名策略 | 直接报名：校验通过后立即创建“已通过”报名；审核型报名：创建“待审核”报名，等待管理员审批。两种规则通过策略接口实现，主流程不写死类型判断。 |
| P2-F05 | 审批操作 | 管理员对待审核报名执行批准或拒绝。**批准时必须再次检查剩余名额**，名额已满则批准失败且不得超出人数上限；拒绝则状态变为已拒绝。 |
| P2-F06 | 状态管理 | 管理报名状态：待审核、已通过、已拒绝、已取消；所有状态变更必须符合 B.2 的规则，非法转换一律拒绝。 |
| P2-F07 | 站内通知 | 报名成功（直接报名）、审核批准、审核拒绝时，向对应学生写入一条站内消息；学生可查看自己的消息列表。通知失败只记录日志，不影响报名/审批结果。 |
| P2-F08 | 统计 | 按活动统计：已通过报名数、待审核数、剩余名额（= capacity − 已通过数）。取消或审批后统计实时同步。 |

## 4. 业务约束（附录 B.2 全文抄录）

以下 7 条为初始版本的完整业务规则，实现与测试均以此为准：

1. 直接报名活动：名额充足且符合基本条件时，创建“已通过”的报名；同时产生站内通知。
2. 审核型活动：提交后为“待审核”；由管理员批准或拒绝。批准时再次检查剩余名额。
3. 名额统计按“已通过”报名计算；待审核报名暂不占用名额。满员后不得再批准新报名。
4. 同一学生对同一活动不得存在两条状态为“待审核”或“已通过”的有效报名。已取消或已拒绝记录保留历史，允许再次申请。
5. 学生可以取消自己的“待审核”或“已通过”报名；活动开始后不允许新增报名。
6. 通知失败应留痕，但不得导致已经合法提交的报名记录无声消失；具体事务边界由学生设计并解释。
7. 活动信息和报名记录必须持久化；管理员删除已有报名的活动时，可采用“拒绝删除并提示”或“软删除”，由学生说明选择。

### 4.1 重点规则（必须落实到代码与测试）

**（1）名额口径：待审核不占名额，只有“已通过”占名额。**
- 剩余名额 = capacity − COUNT(status = 已通过)。
- 待审核数量只用于统计展示（F08），不用于名额校验。

**（2）重复报名判定：同一学生 + 同一活动，同时最多一条【待审核/已通过】有效报名。**
- 已拒绝、已取消属于历史记录，保留但不算有效报名，**允许重新报名**（新建一条记录，不复用旧记录）。
- 实现上以**服务层校验**为主：创建报名前查询该学生该活动是否已存在 PENDING/APPROVED 记录，存在则拒绝。
- 不做数据库层兜底：V1 不采用数据库唯一索引兜底（保持服务层单一校验入口）。

**（3）通知失败只留日志，绝不撤销已成功的报名/审批操作。**
- 事务边界确定为：**业务事务先提交，提交成功后再执行通知**。
- 通知异常仅记录 `WARN/ERROR` 日志，不得向上抛出导致业务回滚，也不得删除已写入的报名记录。
- 同时保证不重复通知：一次状态变更只发一条对应消息（避免事件重复订阅/重试放大）。

**（4）数据必须持久化；删除活动方案已选定：V1 采用“拒绝删除并提示”。**
- 只要活动下存在**任意状态的报名记录**（含已取消、已拒绝，因为 B.2.4 要求保留历史），删除请求一律拒绝，返回提示：“该活动已有报名记录，无法删除”。
- 无任何报名记录的活动，允许物理删除。
- 理由：V1 不引入 `is_deleted` 字段与全局过滤逻辑，改动面最小；杜绝误删导致历史报名与统计丢失，天然满足 C10。
- 未采用“软删除”：留作后续变更候选，不在 V1 预设实现。

### 4.2 其他规则说明与假设（需评审确认）

| 项 | 本文档采取的约定 | 备注 |
|---|---|---|
| 报名时间窗口 | 仅在 `start_at > 当前时间` 时允许新增报名；活动已开始后新增报名返回失败 | 依据 B.1、B.2.5 |
| 取消时间限制 | B.2 只限制“新增报名”，未限制取消；V1 允许随时取消自己的待审核/已通过报名（含活动已开始后） | 本组补充假设；对应自定义测试 T-S1 |
| 取消后的名额 | 已通过报名取消后立即释放名额，可被他人报名/审批占用 | 由“已通过”统计口径推出 |
| 取消是否通知 | P2-F07 只要求“报名结果及审核结果”通知，V1 取消操作不产生站内消息 | 如要求取消也通知，需确认后补充 |
| 审批并发冲突 | 批准前在同一事务内重新读取名额与报名状态；已非“待审核”则拒绝操作 | 对应 B.3“审批冲突”边界要求 |
| 消息已读 | is_read 字段保留，V1 不实现已读/未读交互 | 避免需求外扩 |
| 统计可见性 | 学生端只展示“剩余名额”；已通过数、待审核数等完整统计仅管理员可见 | 本组约定，避免需求外扩 |
| 活动编辑约束 | 允许编辑；若调小 capacity，不得小于当前“已通过”人数 | **本组补充假设，非原始需求**；目的为防止统计出现负剩余名额 |

## 5. 验收用例基线（指导书 3.5，C1 ~ C10）

后续自动化测试与回归测试均以此为基准，用例编号保持不变。

| 用例 | 输入/操作 | 预期结果 |
|---|---|---|
| C1 | 管理员创建直接报名活动，容量 2 | 创建成功，可供学生报名 |
| C2 | 学生 A 报名直接报名活动 | 直接变为“已通过”并通知 |
| C3 | 学生 A 再次提交相同活动报名 | 拒绝重复有效报名 |
| C4 | 学生 B 报名同一活动，名额已满后学生 C 再报名 | B 通过，C 因名额不足失败 |
| C5 | 创建审核型活动，学生 A 申请 | 状态为“待审核” |
| C6 | 管理员批准 A 的待审核报名 | 变为“已通过”且生成通知 |
| C7 | 管理员拒绝另一待审核报名 | 变为“已拒绝”且生成通知 |
| C8 | 批准操作时容量已满 | 批准失败，不超出人数上限 |
| C9 | 学生取消待审核或已通过报名 | 状态“已取消”，统计同步变化 |
| C10 | 重新启动服务，查询活动、报名、通知 | 数据仍一致 |

测试基线补充说明：

- C4 依赖 C1 的容量 2：A 已占 1 个名额，B 占第 2 个后满员，C 报名失败。若单独执行 C4，需先构造“容量已满”的前置数据。
- C3 的“拒绝”指业务失败并给出明确提示，不得产生第二条有效报名记录。
- C8 必须验证：批准失败后报名仍为“待审核”，活动已通过数不超过 capacity。
- C9 需分别覆盖“取消待审核”和“取消已通过”两种情况，并核对 F08 统计中已通过数、待审核数、剩余名额的变化。
- C10 需核对活动、报名、消息三类数据在重启前后完全一致。

| 用例 | 假设来源 | 输入/操作 | 预期结果 |
|---|---|---|---|
