# 变更影响分析（CR-01 年级限定报名 / CR-02 邮件通知）

## 一、变更需求摘要

**CR-01 年级限定直接报名**：Activity 支持“年级限定直接报名”规则；Student 新增 grade（1—4）；仅 grade ∈ {2,3} 可报名此类活动，其他年级收到明确提示；该规则仍遵守名额、活动开始时间、重复报名等公共约束；原有直接报名与审核报名行为不得改变。

**CR-02 邮件通知**：在原有站内消息之外，对“报名通过、审核通过或拒绝”同时发送模拟邮件；由 MockEmailSender 记录收件人、主题、内容、状态与时间；邮件故障必须记录错误但不得回滚已提交的报名；同一业务事件不得重复发送。

## 四、CR-01 详细影响

### 4.1 领域模型与数据

`Student` 增加两个字段：`grade: int`（1—4）与 `email: str`（CR-02 的收件人）。`students` 表迁移为：

```sql
ALTER TABLE students ADD COLUMN grade INTEGER NOT NULL DEFAULT 2
    CHECK (grade BETWEEN 1 AND 4);
ALTER TABLE students ADD COLUMN email TEXT NOT NULL DEFAULT '';
```

SQLite 允许带默认值新增列，因此学生表不需要重建。演示数据补齐为：S001 大二、S002 大三、S003 大一，新增 S004 大四，并写入各自示例邮箱；已有测试继续使用 S001—S003，语义不受影响。

### 4.2 策略契约升级

现状 `initial_status()` 无参数，只能表达“报名后进入什么状态”，无法读取年级，也无法拒绝并给出原因。因此在 `policies/base.py` 升级为决策契约：

```python
@dataclass(frozen=True)
class RegistrationContext:
    student: Student
    activity: Activity

@dataclass(frozen=True)
class PolicyDecision:
    status: RegistrationStatus | None
    rejection_code: str | None = None
    rejection_message: str | None = None

class RegistrationPolicy(Protocol):
    def decide(self, context: RegistrationContext) -> PolicyDecision: ...
    def requires_approval(self) -> bool: ...
```

选择决策对象而不是让策略抛 HTTP 异常：策略不应了解接口语义；拒绝码由服务层统一转为 400，和现有 `BusinessError` 映射保持一致。

`DirectPolicy` 返回 APPROVED、`AuditPolicy` 返回 PENDING，与原行为等价。新增 `GradeLimitedDirectPolicy`：grade ∈ {2,3} 返回 APPROVED，否则返回 `GRADE_NOT_ELIGIBLE` 与“该活动仅面向大二、大三学生”的提示。

不采用“可组合规则链”：当前只有一条资格规则、两种流程，规则链的抽象成本高于收益；若后续出现年级、学院、会员等级等多条资格规则，再在 `PolicyDecision` 内部引入规则组合，重构范围可控。

### 4.3 服务层改动点

`RegistrationService.register` 只调整三处，不改变公共约束的顺序与事务边界：

```text
活动存在 → 活动未开始 → 查重 → 加载学生 → 策略决策
→ 拒绝则抛业务错误 → 通过则按原路径校验名额 → 保存 → 发布事件
```

新增学生加载后，可顺带把“学生不存在”从数据库外键异常变为明确的 `STUDENT_NOT_FOUND`，属于边界完善而非行为变更。

### 4.4 活动类型与数据库约束

`activities.policy_type` 现有 `CHECK (policy_type IN ('DIRECT','APPROVAL'))`，新增 `GRADE_DIRECT` 需要扩展约束。SQLite 不支持直接修改 CHECK，必须重建表：关闭外键 → 事务内建新表并复制数据 → 删除旧表 → 重命名 → 重建索引 → 打开外键 → `PRAGMA foreign_key_check`。

备选方案是把年级范围存成活动字段、沿用 DIRECT 类型；不采用的原因是同一种“直接报名”会分裂成两种语义，策略工厂形同虚设，前端与测试也难以区分。

### 4.5 接口与前端

`POST/PUT /api/admin/activities` 的 `policy_type` 是枚举类型，新增枚举值后自动接受，无需改路由。报名被拒时返回 400，`code=GRADE_NOT_ELIGIBLE`，`message` 为年级提示。

前端需要同步三处：活动创建与编辑的两个下拉框、`POLICY_TEXT` 文案映射、活动卡片与表格的类型展示；年级信息在演示学生选择处标注，便于课堂演示。

## 五、CR-02 详细影响

### 5.1 邮件作为第二个订阅者

新增 `EmailNotificationService` 实现既有 `NotificationListener` 契约，订阅报名状态变更事件。按 CR 文字“报名通过、审核通过或拒绝”，只处理 APPROVED 与 REJECTED；PENDING 仍只发站内消息，站内模板不改。

`RegistrationService` 与 `NotificationService` 均不修改。这正是 V1 观察者设计在本次变更中的直接收益。

### 5.2 发送端口与 Mock 实现

```python
class EmailSender(Protocol):
    def send(self, *, recipient: str, subject: str, content: str) -> None: ...
```

生产装配 `MockEmailSender`，不连接真实邮件服务，只把记录写入 `email_logs`。失败注入放在测试侧，用会抛异常的发送器替换依赖，不在业务代码里保留测试开关。

### 5.3 持久化与去重

```sql
CREATE TABLE email_logs (
    email_id        TEXT PRIMARY KEY,
    event_id        TEXT NOT NULL UNIQUE,
    registration_id TEXT NOT NULL,
    student_id      TEXT NOT NULL,
    recipient       TEXT NOT NULL,
    subject         TEXT NOT NULL,
    content         TEXT NOT NULL,
    status          TEXT NOT NULL CHECK (status IN ('SENT','FAILED')),
    error           TEXT,
    created_at      TEXT NOT NULL
);
```

`event_id` 唯一索引实现“同一业务事件只发一次”，重复事件写入触发冲突后直接跳过并记录日志。相比 V1 的进程内集合，该约束在重启后仍然有效，直接覆盖 CR2-04。

发送失败时写入 `status='FAILED'` 与错误信息的记录，异常在订阅者内部吞掉，不向上抛出。

### 5.4 装配与部署差异

新增仓储与服务依赖，并**同时**在两处完成订阅：

- `project/main.py` 的 `lifespan`（本地 uvicorn）
- `wsgi.py`（PythonAnywhere，WSGI 不触发 lifespan）

V1 已出现过“本地正常、线上不发通知”的问题，本次把订阅装配列为部署检查项：上线后必须看到新报名产生 `email_logs` 记录才算完成。

### 5.5 只读查询接口

为验收与课堂演示增加管理员只读接口 `GET /api/admin/email-logs`，返回最近邮件记录（收件人、主题、状态、时间、错误）。该接口不改变任何写路径；学生端消息面板保持原样。

## 六、设计决策汇总

| 决策点 | 选择 | 理由 |
|---|---|---|
| 年级限定实现方式 | 新增独立策略 | 现有工厂已按类型选择，增量最小，职责清晰 |
| 策略如何拒绝 | 返回决策对象 | 策略不感知 HTTP；服务层统一映射 400 |
| 公共约束位置 | 仍留在服务层 | 名额、开始时间、查重是跨策略不变量 |
| 是否改报名服务主流程 | 仅 3 个接入点 | 不改变约束顺序与“先提交后发布”的事务边界 |
| 邮件实现方式 | 新增观察者 | 与 V1 设计一致，报名服务零改动 |
| 去重方式 | 数据库唯一约束 | 覆盖进程重启，强于内存集合 |
| 真实邮件与重试 | 不做 | 属本次范围外，保持 Mock 可验证 |

## 七、数据库迁移方案

迁移脚本 `scripts/migrate_v2.py`，幂等执行，步骤为：备份数据库文件 → 检查并新增 students 列 → 更新演示学生年级与邮箱 → 重建 activities 表扩展 CHECK → 创建 email_logs 与索引 → 外键与数据行数校验。

回滚方式：恢复备份文件，代码回退到 `baseline-v1`；`change-v2` 标签保留以便对比。测试库由 `reset_db` 按新 SCHEMA 直接建表，不走迁移路径。

## 九、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| activities 表重建失败 | 线上数据损坏 | 迁移前备份；事务执行；迁移后外键检查与行数核对 |
| WSGI 漏订阅邮件 | 线上只有站内消息 | 部署检查清单；线上报名后核对 email_logs |
| 旧测试数据无年级 | 变更测试失败 | 迁移与种子显式补齐演示学生年级 |
| 单例缓存导致串库 | 测试相互影响 | fixture 增加新仓储缓存清理 |
| 前端未同步类型 | 课堂演示看不到新选项 | 三处文案与下拉同步，补充界面验证 |
| 邮件失败日志缺失 | 无法证明不回滚 | 失败记录写入 email_logs，同时输出错误日志 |

## 十、实施顺序与交付物

实施顺序：本文档（先于代码）→ 设计说明 V2 增量与 UML/时序图更新 → 从 `baseline-v1` 建分支 → CR-01 → CR-02 → 新增测试与全量回归 → 数据库迁移与线上部署 → 打 `change-v2` 标签 → 更新实验报告、AI 协作记录与变更对比数据。

## 十一、结论

两项变更均可在现有分层内完成：CR-01 通过升级策略契约与学生数据实现，CR-02 通过新增观察者实现。`RegistrationService` 只在三个接入点改动，不改变公共约束顺序与事务边界；其余改动集中在策略、仓储、装配与前端。该方案满足教师“先影响分析、后 AI 修改”的流程要求，也保留了可回归、可对比、可回滚的证据链。
